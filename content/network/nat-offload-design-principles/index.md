> 本文是《[路由数据面加速器五派对比](/network/datapath-accelerator-five-vendors/)》的工程视角续篇：调研是"别人怎么做的"，这篇是"轮到自己动手时该守住什么"。原则来自主流商用架构的公共机制与我们在自研轻量 NAT 加速器（头部预解析 + 单实例无环微码引擎 + 端口适配器范式）方案收敛过程中的评审沉淀。

## 原则一：头身分离——只动必须动的字节

一个 1500 字节的包，需要"看"和"改"的只有前 64~128 字节包头。加速器的全部价值就在于：**Payload 一步都不动**，包头窗抓进引擎改完贴回。配套动作是校验和也要增量修（RFC 1624 差量公式）而不是整包重算——整包重算等于把加速收益全部还给外存等待时间。

**验收指标**：转发热路径上对 Payload 的读写次数必须为零（可用总线监测或逐指令 trace 证明）。

## 原则二：头长会变——写回地址必须能"伸缩"

不同出口要求的私有头长度不同：USB 类接口前置十几个字节、Wi-Fi TX 前置更长，VLAN/PPPoE 还会动态增删。如果引擎只会"原位置写回"，头长一变，软件就得 `memmove` 搬整个 Payload——加速全白干。

解法：缓冲区预留头部空间，包头在头窗内伸缩后**按新偏移写回，并同步更新描述符的帧偏移与帧长**。一个容易踩的细节：偏移调整后的**最小帧长/padding 计算必须在新偏移上进行**，这条顺序要写进软硬件 ABI，不能留给实现自由发挥。

**验收指标**：切换任意两种出口封装，Payload 搬移字节数 = 0。

## 原则三：建流归软件，转发归硬件——延迟绑定根治首包超车

最隐蔽的坑是**软硬切换乱序**：首包未命中送 CPU 慢吞吞建表；表还没建好，第二个包已经从硬件快车道飞出去了——第 2 包比第 1 包先到。解法（MTK 主线已验证的范式）：

- 流表项带四态：`INVALID / UNBIND / BIND / FIN`；
- 新流命中 `UNBIND` 空项时，**硬件只学习、只计数，包本身送上 CPU**；
- 达到绑定门限后由**软件**把表项提交为 `BIND`——"硬件计包、软件扣扳机"。

前几个包全部走 CPU 慢路径，乱序从物理时间上就不可能发生。另一个待实测的量：UDP 短命流（DNS、QUIC、游戏）要不要绑定——短命流疯狂建表会冲刷流表缓存，绑定门限应按表项存活分布实测来定。

**验收指标**：任意流的前 N 包全部出现在 CPU 路径，无一处硬件先于软件发包。

## 原则四：表项发布必须原子——最后一步只翻一个字

流表项几十上百字节，32 位总线要写十几次。写到一半被硬件命中，解析出来的就是错乱表项。解法（MTK 主线范式）：把状态位放在表项第一个字——先写其余字段（此时状态位非 `BIND`），插内存写屏障，**最后用单条 32 位写翻转状态位**。硬件要么看不见，看见必是完整表项。

**验收指标**：并发压测下，硬件命中的表项 100% 通过合法性校验（可用注入"半写"用例验证）。

## 原则五：微码必须无环、定长——让编译期证明最坏时延

微码引擎最大的诱惑是"图灵完备"，最大的陷阱也是它。多核微码并发（博通 Runner 早期路线的教训）带来的跨核保序与调试成本极高；无环定长指令序列则可以：静态穷举最坏周期数、编译期证明无死循环、逐指令与模拟器对拍。给每条微码路径配硬件看门狗兜底，超时强制上送 CPU。

**验收指标**：每条微码插件的最坏执行周期数在编译期给出上界，并在对拍中实测确认。

## 原则六：大表放片外，小缓存放片上——但要实测后再定档

几千条双向连接的全量流表往往超出片上 SRAM 预算，分级查表（片上缓存 + 外部大表）是必然选择。两个容易犯的错：

1. **直接引用别人的命中率**——命中率与缓存容量挂钩，而"大象流命中率"与"长尾连接数"是两个量纲，UDP 短命流会冲刷缓存；
2. **忘记算兜底**——即便缓存 100% miss，每包一次外部 DDR 的 64 字节 burst 也应仍在包处理时间预算内。分级的下限风险是可控的，上限收益要用**自己的活跃流工作集实测**来定档，数据说话。

**验收指标**：以目标业务工作集实测命中率与 miss 时延 p99，据此冻结缓存容量档位。

## 原则七：背压要双水位——绝不让慢出口抽干全局接收池

这是最容易被忽视、后果最致命的一条。设想：5G 口 1 Gbps 猛收包，零拷贝把接收缓冲借给 Wi-Fi 口发送；手机进了电梯，Wi-Fi 变慢，几百个缓冲全卡在发送队列还不同来——几毫秒后**全局接收池被抽干，连控制包和释放信号都收不进来，整机死锁**。Marvell PPv2 的缓冲管理器给出了标准答案（主线代码可见）：

- **源端保命水位**：空闲缓冲低于阈值时，严禁零拷贝借出（改走拷贝或当场丢弃归还）；
- **出口配额**：每个出口最多挂 N 个未完成包，超额硬件 tail-drop 并精确计数。

**验收指标**：人为拖慢任意一个出口到极限速率，其余端口的收发与控制面不受影响（死锁注入测试）。

## 原则八：控制命令与数据同环——屏障语义要讲清边界

流表失效、ARP 变化、端口复位时，软件需要确认加速器里没有"在飞的旧包"。一个轻量做法：把控制命令做成一种不访问包内存的描述符，与数据包排进同一条 FIFO——**当命令描述符从单实例引擎弹出时，证明此前入环的旧代包已全部离开引擎**。

但必须说清语义边界：这只能证明"引擎内已排空"，**不等于"已提交到端口 TX 环的包已离场"**——端口级静止需要端口 DMA 静止握手（参考高通 IPA：其 pipeline-clear 只在复位路径使用，且靠探针包确认，同样不证明端口级排空）。两类屏障混用是常见的事故来源。

**验收指标**：流撤销/复位用例中，旧代包与新代包零交叉；端口级回收按 DMA 静止握手闭环。

## 小结

| # | 原则 | 一句话验收 |
|---|---|---|
| 1 | 头身分离 | Payload 读写次数 = 0 |
| 2 | 头窗可伸缩 | 换封装 Payload 搬移 = 0 |
| 3 | 延迟绑定 | 前 N 包全走 CPU，零乱序 |
| 4 | 原子发布 | 半写表项命中 = 0 |
| 5 | 无环定长微码 | 最坏周期编译期可证 |
| 6 | 分级流表 | 命中率用自己工作集实测 |
| 7 | 双水位背压 | 慢出口拖垮整机 = 不可能 |
| 8 | 同环屏障 | 引擎内排空 ≠ 端口静止，分开验证 |

这些原则的验证不必等到流片——下一篇《[RTL 之前先把风险拆掉](/network/datapath-verify-ladder/)》讲怎么用软件基线、可执行规格和 QEMU 把它们逐条闭环。
