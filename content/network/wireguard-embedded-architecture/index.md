> 背景：MiFi（随身 WiFi）插 4G/5G 卡后拿到的是运营商 CGNAT 深层私网地址，公网连不进设备。本文复盘在 FreeRTOS + lwIP 平台上落地 WireGuard 隧道的架构决策。NAT 穿透的原理背景见《[双重 NAT 问题模型](/network/dual-nat-traversal/)》。

## 为什么是 WireGuard 而不是别的

需求有三条硬约束：**穿透一切 NAT**（设备主动外连）、**点对点加密**（云端 ↔ 设备专属通道）、**物理级流量隔离**（下挂用户的手机流量绝不能泄进运维隧道，隧道流量也绝不能摸进用户局域网）。对比结论：自研 TLS 代理要自己发明整个安全协议；商用方案引入不可控闭源组件；WireGuard 代码量小、形式化验证过、内核态/用户态都有成熟实现——在嵌入式上是"安全感/工程量"比最优解。设备侧只做出站 UDP，天然穿透 CGNAT。

## 五层架构：职责切干净，系统才稳

```text
L5  业务插件层    心跳/注册 · 日志上报(规划) · 远程控制(规划)
L4  总线与控制面  隧道服务总线(调度/队列/生命周期) · WG 会话管理器 · CLI 诊断面
L3  协议与算法    wireguard-lwip(Noise 握手/ChaCha20-Poly1305) · 纯逻辑校验器 · 协议装包器
L2  凭据与安全    私钥安全存储 · 硬件熵 · DRBG
L1  网络底层      lwIP 内核 · WAN 物理网卡 · wg0 虚拟隧道网卡
```

三条分层纪律值得单独说：

1. **L3 平台无关**：协议、算法、校验逻辑是纯函数，不碰 FreeRTOS API——换平台只动 L1/L2 胶水；
2. **L4 独立于 L5**：业务插件通过服务总线挂载，隧道系统不知道"心跳"或"日志"的存在——新业务 = 新插件，隧道代码零改动；
3. **CLI 诊断面是独立模块**，不是散落的 printf：`wg status / start / stop` 串口命令与业务共用同一套状态机，避免"调试路径和生产路径行为不一致"的经典坑。

## 安全边界：四道闸

隧道一旦打通，它就是一条进内网的线，边界设计比隧道本身更重要：

- **网段白名单**：只有发往隧道对端网段的包才允许进 wg0——下挂用户的上网流量与运维流量物理隔离；
- **IP 防伪造校验**：从隧道收到的包，源地址必须在对端声明的范围内，否则丢弃（防隧道内注入）；
- **首版最小暴露**：只开放设备本机虚拟 IP，不转发 LAN、不做以太网桥接——需要访问下挂设备时再逐项放开，每放开一项都是一次显式的安全评审；
- **密钥不入固件镜像**：私钥放安全存储区、运行时加载；WAN 变化后要求新熵手动重启会话，而不是自动重连（防降级重放）。

## 一个真实教训：可用性优先于优雅

早期版本曾设计过"WG 状态与 WAN 状态全自动联动"——WAN 起来自动拉起隧道。真机上很快翻车：蜂窝网络抖动导致隧道反复重握手，把 CPU 和电量都耗在无意义的 Noise 握手上。最终回退为**手动启停 + 状态可观测**：运维人员通过 CLI/云端指令控制会话，状态变化全部上报。嵌入式远程运维的第一原则不是"全自动"，而是"每一步都可解释"。

## 结语

这套架构的本质是**把"加密管道"和"业务"解耦**：管道层（L1-L4）一次做对，业务层（L5）按需插拔。相关阅读：《[NAT 动画演示](/network/nat-animation-demo/)》看包如何在网关被改写；《[路由数据面加速器五派对比](/network/datapath-accelerator-five-vendors/)》看数据面加速如何与隧道共存。
